# hardware

整机硬件监控。十枚面板组件加一份 node 侧采样。

## 它做什么

给概览页添十枚组件：**系统**（CPU 与内存合成一张卡）、CPU、内存、SWAP、显卡、磁盘与读写、网络、
进程表、系统信息、Redis。

「整机」是它存在的全部理由 —— 内核已有一套**本进程**的占用，而这个插件给的是整台机器。故环上
分三段：**本核心占用、其他占用、空闲**，三段合起来恰是一整圈，每一种颜色都有名字。

「系统」那一枚是默认上板的那一个：CPU 与内存的型号、核数、总量、使用量列成一张事实表，右侧两枚
带图例的环。分成两格之后使用者的视线要来回两趟，而两格之间还夹着别的卡片。

它同时是**面板插件包的完整范例**：浏览器侧十个组件、node 侧六条采样路由、一份自带样式表、一份配置
声明、一个第三方依赖。想知道面板插件能做到什么程度，读它。

## 怎么装

在**面板商店**里装（不是插件市场 —— 那是内核插件的市场，两者的索引与落点都不同）。装完商店会自己把
依赖（`systeminformation`）装上，再跑一次 `pnpm run build` —— 后者不能省：node 侧入口是
`dist/index.js`，而 `dist/` 不在仓库里，不编译则十枚组件全都取数失败。确认框会把这两步列出来。

装完**要重载一次 webui**：node 侧入口只在 webui 的 `setup()` 时加载。纯浏览器侧的包刷新页面即可，
但这个包有 node 侧。

十枚里九枚默认不上板，在编辑态的「已移除」一栏里取用。默认只上「系统」那一枚 —— 它接替 webui 撤掉的
本进程 CPU 环与显卡环，否则升级后的概览页会**少掉**两枚环而不是换掉它们。CPU 与内存那两枚仍在包里、
仍可单独上板（有人只想要一枚环），但默认不上：它们与「系统」取自同一份采样，同时上板会让同一个数在
一页上出现两次。

## 关键实现

**型号与占用分开探，型号只探一次。** 实测 `si.cpu()` 2131ms、`si.graphics()` 2250ms、
`si.memLayout()` 683ms 且都不缓存，而面板按 5 秒轮询。首次请求不等它探完（否则第一次打开面板要卡
五秒），型号在下一轮出现。

**整机 CPU 用 `os.cpus()` 的时间累计量作差，不用 `si.currentLoad()`。** 后者 511ms 且每次起一个
子进程，前者是纯内存读取。代价是要两次采样才有第一个数 —— 首次**不返回该字段**而非记 0：0 会被
读成「机器闲着」，而真相是「还没有第二个采样点」。

**显卡的占用率复用内核已公开的 `probeGpus()`，不自己再写一份 CSV 解析。** 两份解析迟早给出两个数，
而「同一块卡在两处显示不同占用」最难察觉。代价是内核与本插件各 spawn 一次 nvidia-smi —— 明知而
接受：省下那次 spawn 换不来「两处口径一致」。

**双色环的两段是包含关系，不是并列关系。** 本进程占用本就算在整机占用里，故两段首尾相接铺在同一
圈上。而两个数来自两个接口、两个采样时刻，故可能出现「本进程 5%、整机 3%」这种瞬时矛盾 ——
本进程那段要夹在整机之内，否则画面上像是「机器人用得比整台机器还多」。

**环旁的图例分三段：本核心 / 其他占用 / 空闲。** 只画两段时留下一个读不出来的问题 —— 整机 29% 里
有多少不是机器人干的？三段之后环上每一种颜色都有名字（含环底那圈没被覆盖的部分），且三行加起来恰是
100%。**「其他占用」是算出来的，不是测出来的**：没有任何接口会给「除本进程之外的占用」，它是整机减
本进程 —— 故整机测不到时这一条也给破折号而非 0%，一条「其他占用 0%」会被读成「这台机器上只有机器人
在跑」。

**本进程那一段的颜色由本包自带的样式表给出。** 面板样式表里没有 `.ring-own`，只有 `.ring-fill` 的
灰色兜底 —— 缺这一份样式时「双色环」实际是单色的，两段首尾相接处看不出分界，而那条分界正是「其中
多少是机器人」的唯一可见凭据。故本包在 `package.json` 里声明 `webuiPanel.style`，那份 css 的每条
选择器会被面板限定到本包之后才注入。

**环的几何写在 `src/rings.ts`（TypeScript）而不在 `widgets/`。** widgets 是浏览器侧的裸 js、不在
用例覆盖之内，而 dasharray 算错不报错、只表现为「环画得不对」。故几何放 `src/` 由 vitest 钉住，
浏览器侧 import 它的编译产物 —— 前提是该模块**不 import 任何东西**，否则浏览器那侧会在 import 时
报错。

**采样拆成六条路由而不是一条大的。** 没上板的组件一次请求都不发；合成一条的话，只想看 CPU 的人
也要为进程表付一次 `si.processes()`。

**不引任何 redis 客户端库。** 要做的只有「发一条 `INFO` 读回一段文本」，约三十行；客户端库带来的
是连接池、集群、Lua、管道与数百 KB 产物，没有一项是这件事需要的。而面板插件包的依赖要使用者自己
装，每个依赖都是一次真实的等待。

**默认不探测任何对外地址。** 出厂就带默认目标等于让这台机器每 5 秒向第三方发一次请求，而使用者
没要求过。目标由配置给出，空配置时组件显示「未配置」并说明怎么加。

**不给「结束进程」之类的动作。** 这是只读的面板组件；一个能杀进程的后台页面是另一个量级的东西
（要确认、要审计、要权限），不该顺手做出来。

## 源码在哪

[Yunzai-NG/hardware-plugin](https://github.com/Yunzai-NG/hardware-plugin)

| 路径 | 内容 |
|---|---|
| `index.js` | 浏览器入口，把十枚组件汇总成一份清单 |
| `widgets/hardware-system.js` | 「系统」那一枚：CPU 与内存合一，两枚带三段图例的环 |
| `widgets/*.js` | 其余九枚；`widgets/lib/store.js` 是共用的取数与画法 |
| `style.css` | 包自带的样式表（由 `webuiPanel.style` 声明）：图例、两栏布局，与环上本进程那一段的颜色 |
| `src/index.ts` | node 侧入口，六条采样路由 |
| `src/probe.ts` | 整机 CPU / 内存 / 显卡与一次性的硬件型号 |
| `src/rings.ts` | 双色环的几何与三段图例的比例（浏览器侧也用它的编译产物） |
| `src/disks.ts` / `net.ts` / `processes.ts` / `sysinfo.ts` / `redis.ts` | 各类采样 |
| `package.json` 的 `webuiPanel` | node 侧入口路径与配置声明 |
