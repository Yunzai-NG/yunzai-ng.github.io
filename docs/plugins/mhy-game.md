# mhy-game

米哈游游戏查询：原神、星穹铁道、绝区零。

## 它做什么

绑定 Cookie 之后查体力、每日、深渊、抽卡记录一类的东西，结果以图片形式回复（经渲染器出图）。

对写插件的人来说，它是**风控与凭据管理**这一类问题的范例：一个要长期使用第三方账号凭据的插件，
该怎么存、怎么用、怎么在被风控时不把事情弄得更糟。

## 怎么装

在插件市场里装。它需要 `renderer-puppeteer` 才能出图 —— 没有渲染器时命令仍然可用，只是退回
文字回复。

装完由使用者自己绑定 Cookie（私聊机器人发送绑定命令）。**Cookie 是账号凭据**，故：

::: danger 不要把 Cookie 贴进群聊
它等同于账号的登录态。插件只接受私聊绑定，且日志里一律打码。
:::

## 关键实现

**绑定 Cookie 时即确定设备，此后不再更换。** 米游社把连续出现超过一天的设备视作常用设备、风控随之
放宽；设备一换，验证码、`1034`、`-100` 就成片出现。故这个插件的每个写操作都要先确认「这会不会
导致已有账号换设备」，结论必须为否。见 `src/device.ts`。

**虚拟设备由账号标识确定性派生。** 存储只是缓存 —— KV 丢了也能原样还原，故任何读取路径在数据缺失
时直接重算而不报错。使用者也可以绑定真机，那是为了直接复用「手机上刚登录过、已属常用设备」的那
一台，省掉重新养一天。

**`device_fp` 与 `device_id` 绑定。** 换设备时旧 fp 必须立即作废，否则会出现「A 设备的指纹配 B 设备
的机型」这种明显不自洽的组合 —— 做法是在 fp 记录里存下取用时的 device_id，不依赖调用方主动清理。

**多 Cookie 轮换有冷却。** 一个 Cookie 被风控之后立刻换下一个，只会让第二个也进同一个坑；故失败的
那个进冷却，而不是无脑轮转。

**请求签名（DS）按接口版本分两套。** 米游社的老接口与新接口签名算法不同，混用会得到一个语义完全
无关的错误码。见 `src/sign.ts`。

**出图走模板而不是拼字符串。** 模板在 `templates/`，数据由 `src/views/` 整形 —— 于是「查询逻辑」
与「长什么样」分开，改版式不必碰请求代码。

## 源码在哪

[Yunzai-NG/mhy-game-plugin](https://github.com/Yunzai-NG/mhy-game-plugin)

| 路径 | 内容 |
|---|---|
| `src/index.ts` | 命令注册与配置 schema |
| `src/device.ts` / `device-profile.ts` | 设备的存储与确定性派生 |
| `src/ck.ts` | Cookie 池与冷却 |
| `src/client.ts` / `sign.ts` | 请求与签名 |
| `src/user.ts` | 账号与 QQ 的绑定关系 |
| `src/gacha.ts` | 抽卡记录 |
| `src/views/` | 把接口数据整形成模板要的形状 |
| `templates/` | art-template 模板 |
