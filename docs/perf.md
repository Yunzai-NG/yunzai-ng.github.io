# 性能基线

以下数据均为本机实测，测量脚本包含在仓库中，可自行复现：

```
pnpm run bench:startup     # 启动耗时与启动后 heap
pnpm run bench:memory      # 内存与吞吐基线
pnpm run check:firstrun    # 空配置目录下官方插件能否全部加载
```

两个压测脚本都可以加 `--core <目录>` 换一份内核（如 `npm i @yunzai-ng/core@0.6.5` 装下来的那份），
`bench:startup` 给多个 `--core` 时交替跑、逐份取中位数。插件 import 到的内核也一并换成那一份，进程里只有一份内核。

测试环境：Node v22.22.3 / win32-x64，0.6.5 与 0.7.0 都是 npm 上的发布产物。**官方插件**指 `webui`（面板）
+ `adapter-onebot` + `renderer-puppeteer` + `steward`（运维），即一份接 QQ、带面板、能出图的常见部署；四者在
两个版本上均加载成功，浏览器未启动。

## 启动

从 import 内核到 `app.start()` 返回的 CPU 时间，0.6.5 与 0.7.0 交替各跑 7 次取中位数（墙钟受机器上其他进程
影响大，不作依据；Node 自身启动约 120 ms 不计在内）：

| | 0.6.5 | 0.7.0 | 启动后 heap（0.6.5 → 0.7.0） |
|---|---|---|---|
| 纯内核，不开服务器 | 1751 ms | **141 ms** | 17.6 → **13.1** MB |
| 纯内核，开服务器 | 2281 ms | **281 ms** | 20.0 → **17.2** MB |
| 内核 + 面板（webui） | 2235 ms | **328 ms** | 20.7 → **18.0** MB |
| 内核 + 四个官方插件 | 3501 ms | **1921 ms** | 25.3 → **22.8** MB |

四个插件里大头是 renderer-puppeteer：在 0.7.0 上逐个单独带上，webui、steward 各加 60～80 ms，adapter-onebot
约 250 ms，renderer-puppeteer 约 1.3 秒 —— 它在加载时就 import 了 puppeteer-core 与 `@puppeteer/browsers`，
哪怕一张图都还没出。

启动时间几乎全花在**加载代码**上，而不在内核自己的初始化（建目录、读配置、开存储合计数十毫秒）。
0.7.0 的办法分两类。

**少读文件。** 内核发布产物由 esbuild 打包：内核自身 69 个模块连同 yaml、fastify、ws 的几百个文件合成
少数几个，Node 逐个解析、打开、编译小文件的开销（Windows 上还有杀毒扫描）随之消失。单这一项，
带面板启动约省三分之二。原生模块、undici、croner 不打包。

**不用就不加载：**

- Fastify 不编译路由 schema。服务器只有四条 catch-all 路由、一个 schema 都不声明，而缺省的 ajv 编译器
  在构造时同步加载，约占建服务器耗时的九成；
- Fastify 与 WebSocket 插件在建服务器时才加载，关掉面板的部署一个都不加载；
- HTTP 客户端（undici）在首个请求时才加载，启动完成后再在后台预载，首个请求不必等它；
- 日志直接构造记录，不再经 pino 序列化成 JSON 再解析回来；
- 静态文件由 `@fastify/send` 直接发送，首个静态请求时才加载。

## 内存

每格 RSS / heap，0.6.5 与 0.7.0 交替各跑 3 次取中位数：

| | 空载 | 1 万条后 | GC 后 | 停机后 |
|---|---|---|---|---|
| 纯内核，0.6.5 | 102.7 / 17.7 MB | 117.6 / 31.0 MB | 117.2 / 18.4 MB | 117.4 / 18.4 MB |
| 纯内核，**0.7.0** | **81.7 / 13.3** MB | 92.9 / 18.5 MB | 92.7 / **13.9** MB | 92.6 / 13.9 MB |
| 内核 + 四个官方插件，0.6.5 | 138.0 / 25.5 MB | 138.6 / 35.2 MB | 138.8 / 26.2 MB | 138.9 / 26.1 MB |
| 内核 + 四个官方插件，**0.7.0** | **114.1 / 22.9** MB | 125.7 / 34.5 MB | 125.9 / **23.6** MB | 126.0 / 23.5 MB |

配置为 `store.driver: memory`；纯内核不开服务器，带官方插件时服务器开在本机一个空闲端口上（面板离了服务器
挂不上）。空载 heap 里含 0.7.0 启动后预载的 HTTP 客户端（约 4 MB）。

**应关注 heap 一列。** 1 万条消息处理完毕并执行 GC 之后，heap 与空载相差不到 1 MB
（0.7.0 纯内核 13.3 → 13.9，带插件 22.9 → 23.6），即这 1 万条消息未留下驻留对象：事件对象、
渲染上下文与命令记录均已回收。这与[插件开发](plugin-api.md)中 DisposalRegistry 所保证的
性质一致，区别在于此处度量的是稳态而非卸载。

**RSS 不会回落，此为正常现象。** V8 向操作系统申请过的地址空间不再归还，因此 RSS 仅表示
历史最高水位，据其判断是否存在泄漏必然误判。判断泄漏应延长运行时间并比较**多轮 GC 后的 heap**，
而非 RSS。

四个官方插件在 0.7.0 上合计约增加 10 MB 空载 heap、30 MB 空载 RSS，后者多是 renderer-puppeteer 与面板加载的代码。
不需要的插件写入 `plugins.disabled` 即完全不加载，亦不占用内存。

**新生代上限。** 上表以 Node 缺省参数测得。V8 在 64 位上把新生代放到 16MB，消息一阵密集就涨上去、
不再归还，RSS 里有相当一块是它。`yzng start` 的自带守护 fork 内核时带上 `--max-semi-space-size=4`，
同一场景（0.7.0 + 四个官方插件，1 万条）三次的中位数：

| 新生代上限 | 空载 RSS | 1 万条后 RSS | 吞吐 |
|---|---|---|---|
| 16 MB（缺省） | 114.6 MB | 125.8 MB | 约 4.2 万条/秒 |
| **4 MB** | **109.2 MB** | **109.6 MB** | 约 4.0 万条/秒 |
| 2 MB | 105.2 MB | 106.0 MB | 约 3.6 万条/秒 |

heap 三者相同。4MB 与缺省的吞吐差在本机测量波动之内，却省下一阵密集消息涨上去的那 16 MB；再往下压省得不多、
吞吐三次都更低，故取 4MB。
以 pm2 / systemd 托管时内核不经自带守护，参数要自己加，见[部署](deploy.md)。

## 吞吐

| | 0.6.5 | 0.7.0 |
|---|---|---|
| 纯内核 | 282 ms，约 3.5 万条/秒 | **187 ms，约 5.3 万条/秒** |
| 内核 + 四个官方插件 | 411 ms，约 2.4 万条/秒 | **237 ms，约 4.2 万条/秒** |

1 万条的耗时与折算，三次中位数。单进程、投递限流（每批 50 条，上一批走完管线后再投下一批）下的数据，
含中间件链、命令路由匹配与 2000 次经 Mock 适配器的回复。0.7.0 的提升来自日志不再序列化再解析、事件 id 的
随机数改从池里取。加载四个插件使吞吐下降约五分之一，主要来自它们挂在每条消息上的中间件与事件监听（面板的
消息统计即是其一）。

该量级远高于实际需要：数百人规模的群聊一日的消息量在此不到一秒即可处理完毕。实际瓶颈不在
消息分发，而在渲染出图与上游 API，两者均属插件职责。

### 度量方式

`scripts/bench-memory.mjs` 的文件头记录了三条取舍，调整数据前应先阅读该段。要点如下：

1. **每个场景使用独立进程。** 在同一进程内先后跑完两个场景时，V8 堆已经增长，
   场景二的空载值会继承上一轮水位。父进程仅负责调度与汇总。
2. **投递需限流。** `submit()` 同步返回而内核异步处理，以一个循环灌入 1 万条度量的是
   瞬时积压峰值，而非稳态占用。
3. **每次取样前连续执行三轮 GC 并让出事件循环。** 单次 `gc()` 后立即读数往往尚未完成回收，
   同一份代码两次运行可相差十余 MB。

日志级别保持缺省的 `info`：分发器为每一条收到的消息记录一行，压测中这 1 万行日志的开销
一并计入上述数据，与实际部署状态一致。

## 复现时的正常波动

同一台机器上重复运行，RSS 各项浮动约 ±1 MB，吞吐浮动约 ±15%（批次小、单批耗时不到一毫秒，
受调度影响大）。超出该范围才需要排查。明细每次写入 `temp/bench-memory-<内核版本>.json` 与 `temp/bench-startup.json`。

带官方插件的场景要求四个插件以仓库形式放在与内核仓库并列的 `repos/` 下且已构建；脚本在临时主目录里给每个插件
建一个真目录、把仓库里的子目录链进去（0.7.0 之前的内核不认链接过来的插件目录），跑完先拆链接再删目录。

## 低内存设备

Termux 与小内存 VPS 上占用内存的主体是 Chromium 而非内核。调整以下三项即可，其余无须改动：

```yaml
store:
  driver: json        # 纯 JS 实现，不使用原生模块
message:
  concurrency: 2      # 修改后需重启；避免多张图同时渲染耗尽内存
render:
  scale: 1
```

此外可将 renderer-puppeteer 的 `pages` 设为 1、`restartAfter` 调小（如 50）：Chromium
长时间运行时内存持续增长，定期重启是代价最低的处置方式。详见
[配置](config.md#低内存设备)与[渲染与模板](renderer.md#低内存设备)。

## 与旧框架的结构性差异

此处不做并排跑分：旧框架硬依赖 Redis 与 genshin 插件，缺少任一即无法启动，因此不存在可比的
空载值。但以下结构性差异可以直接指出：

| 旧实现 | 本实现 |
|---|---|
| 每条消息实例化一遍全部插件类 | 插件实例仅一份，命令是注册表中的条目 |
| 每条消息线性尝试全部正则 | 按前缀首字符分桶，仅尝试可能命中的少数候选 |
| `Renderer.html = {}` 只增不减，每个模板挂一个 `fs.watch` | 编译缓存有界（缺省 128 条）、按 mtime 失效、不占用 watcher |
| OneBot 适配器 `LoadAll()` 全量预载群成员 | 按需拉取，配合 LRU 与 TTL |
| 媒体全链路 base64 往返 | 优先 `file://`、URL 或直接传递 Buffer |
| 热重载不回收 watcher / cron / handler | 每插件一份 DisposalRegistry，卸载时逐项回收 |

前两项体现在上文的吞吐数据中；后四项须在长时间运行与真机环境下才能观测，该部分尚无可发布的
实测数据，待真机联调完成后补充。
