# 性能基线

以下数据均为本机实测，测量脚本包含在仓库中，可自行复现：

```
pnpm run bench:memory      # 内存与吞吐基线
pnpm run check:firstrun    # 空配置目录下官方插件能否全部加载
```

测试环境：Node v22.22.3 / win32-x64，内核 0.7.0。每个场景投递 10000 条消息，其中 2000 条命中
`#ping` 并实际产生一次回复 —— 真实群聊中绝大多数消息不命中任何命令，而"命中并回复"是开销最大的
路径，两者均需覆盖。

## 启动

同一台机器上与 0.6.5 对比，取 9 次的 CPU 时间中位数（墙钟受机器上其他进程影响大，不作依据）：

| | 0.6.5 | 0.7.0 |
|---|---|---|
| 带面板（`server.enable: true`） | 2328 ms | **1125 ms** |
| 不带面板 | 1828 ms | **485 ms** |
| 启动后 heap | 24 MB | **13 MB** |
| 加载的 CommonJS 模块 | 543 个 | **243 个** |
| `yzng doctor`（墙钟） | 1938 ms | **545 ms** |

启动时间几乎全花在**加载依赖**上，而不在内核自己的初始化（建目录、读配置、开存储合计数十毫秒）。
故 0.7.0 的办法都是「不用就不加载」：

- Fastify 不编译路由 schema。服务器只有四条 catch-all 路由、一个 schema 都不声明，而缺省的 ajv 编译器
  在构造时同步加载，约占建服务器耗时的九成；
- Fastify 与 WebSocket 插件在建服务器时才加载，关掉面板的部署一个都不加载；
- HTTP 客户端（undici）在首个请求时才加载，启动完成后再在后台预载，首个请求不必等它；
- yaml 在首次读写配置时才加载，只用内核一两个函数的 CLI 命令一份配置都不读；
- 日志直接构造记录，不再经 pino 序列化成 JSON 再解析回来；
- 静态文件由 `@fastify/send` 直接发送，首个静态请求时才加载。

## 内存

| | 空载 RSS / heap | 1 万条后 | GC 后 | 停机后 |
|---|---|---|---|---|
| 纯内核（不加载插件） | 64.5 / 13.5 MB | 72.9 / 17.9 MB | 73.2 / **14.0** MB | 73.3 / 14.1 MB |
| 内核 + 三个官方插件 | 79.7 / 20.8 MB | 95.9 / 34.4 MB | 95.3 / **21.3** MB | 95.4 / 21.3 MB |

官方插件指 `adapter-napcat` + `renderer-puppeteer` + `yenai-state`，三者均加载成功且浏览器未启动。
配置为 `store.driver: memory`、`server.enable: false`，使被测范围收敛在消息管线上。空载 heap 里含
启动后预载的 HTTP 客户端（约 4 MB）。

**应关注 heap 一列。** 1 万条消息处理完毕并执行 GC 之后，heap 与空载相差 0.5 MB 以内
（纯内核 13.5 → 14.0，带插件 20.8 → 21.3），即这 1 万条消息未留下驻留对象：事件对象、
渲染上下文与命令记录均已回收。这与[插件开发](plugin-api.md)中 DisposalRegistry 所保证的
性质一致，区别在于此处度量的是稳态而非卸载。

**RSS 不会回落，此为正常现象。** V8 向操作系统申请过的地址空间不再归还，因此 RSS 仅表示
历史最高水位，据其判断是否存在泄漏必然误判。判断泄漏应延长运行时间并比较**多轮 GC 后的 heap**，
而非 RSS。

三个官方插件合计约增加 7 MB 空载 heap。不需要的插件写入 `plugins.disabled` 即完全不加载，
亦不占用内存。

## 吞吐

| | 1 万条耗时 | 折算 |
|---|---|---|
| 纯内核 | 142 ms | 约 7 万条/秒 |
| 内核 + 三个官方插件 | 191 ms | 约 5.2 万条/秒 |

单进程、投递限流（每批 50 条，上一批走完管线后再投下一批）下的数据，含中间件链、命令路由
匹配与 2000 次经 Mock 适配器的回复。同一脚本跑 0.6.5 约 3.7 万条/秒；提升来自日志不再
序列化再解析、事件 id 的随机数改从池里取。加载三个插件使吞吐下降约四分之一，主要来自它们注册的中间件。

该量级远高于实际需要：数百人规模的群聊一日的消息量在此不到一秒即可处理完毕。实际瓶颈不在
消息分发，而在渲染出图与上游 API，两者均属插件职责。

### 度量方式

`scripts/bench-memory.mjs` 的文件头记录了三条取舍，调整数据前应先阅读该段。要点如下：

1. **每个场景使用独立进程。** 在同一进程内先后跑完两个场景时，V8 堆已经增长，
   场景二的空载值会继承上一轮水位。父进程仅负责调度与汇总。
2. **投递需限流。** `submit()` 同步返回而内核异步处理，以一个循环灌入 1 万条度量的是
   瞬时积压峰值，而非稳态占用。
3. **每次取样前连续执行三轮 GC 并让出事件循环。** 单次 `gc()` 后立即读数往往尚未完成回收，
   同一份代码两次运行可相差十余 MB。

日志级别保持缺省的 `info`：分发器为每一条收到的消息记录一行，压测中这 1 万行日志的开销
一并计入上述数据，与实际部署状态一致。

## 复现时的正常波动

同一台机器上重复运行，RSS 各项浮动约 ±1 MB，吞吐浮动约 ±15%（批次小、单批耗时不到一毫秒，
受调度影响大）。超出该范围才需要排查。明细每次写入 `temp/bench-memory.json`。

场景二要求三个官方插件以仓库形式放在与内核仓库并列的 `repos/` 下且已构建；脚本把它们
链进临时目录加载，跑完先拆链接再删目录。

## 低内存设备

Termux 与小内存 VPS 上占用内存的主体是 Chromium 而非内核。调整以下三项即可，其余无须改动：

```yaml
store:
  driver: json        # 纯 JS 实现，不使用原生模块
message:
  concurrency: 2      # 修改后需重启；避免多张图同时渲染耗尽内存
render:
  scale: 1
```

此外可将 renderer-puppeteer 的 `pages` 设为 1、`restartAfter` 调小（如 50）：Chromium
长时间运行时内存持续增长，定期重启是代价最低的处置方式。详见
[配置](config.md#低内存设备)与[渲染与模板](renderer.md#低内存设备)。

## 与旧框架的结构性差异

此处不做并排跑分：旧框架硬依赖 Redis 与 genshin 插件，缺少任一即无法启动，因此不存在可比的
空载值。但以下结构性差异可以直接指出：

| 旧实现 | 本实现 |
|---|---|
| 每条消息实例化一遍全部插件类 | 插件实例仅一份，命令是注册表中的条目 |
| 每条消息线性尝试全部正则 | 按前缀首字符分桶，仅尝试可能命中的少数候选 |
| `Renderer.html = {}` 只增不减，每个模板挂一个 `fs.watch` | 编译缓存有界（缺省 128 条）、按 mtime 失效、不占用 watcher |
| OneBot 适配器 `LoadAll()` 全量预载群成员 | 按需拉取，配合 LRU 与 TTL |
| 媒体全链路 base64 往返 | 优先 `file://`、URL 或直接传递 Buffer |
| 热重载不回收 watcher / cron / handler | 每插件一份 DisposalRegistry，卸载时逐项回收 |

前两项体现在上文的吞吐数据中；后四项须在长时间运行与真机环境下才能观测，该部分尚无可发布的
实测数据，待真机联调完成后补充。
